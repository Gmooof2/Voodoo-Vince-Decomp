# Voodoo Vince Decomp

A **matching decompilation** of *Voodoo Vince* (Xbox, Beep Industries, 2003; the USA release): C++ source that, compiled with Visual Studio .NET 2003, reproduces the retail code **byte for byte**, one function at a time. It is early work: most of the game is not matched yet.

"Matched" has a narrow meaning that a machine checks. A function either compiles to exactly retail's bytes or it doesn't count, and "does the same thing" is never enough. What this repository claims is what `python tools/gate.py` proves on your own copy of the game.

## Where it stands

| Metric | Matched | Of | % |
|---|---:|---:|---:|
| Game functions | 2,797 | 7,869 | 35.54% |
| Game code bytes | 277,005 | 1,170,670 | 23.66% |

Current figures, and exactly what each one is measured against, are in [`docs/progress.md`](docs/progress.md), generated by `tools/progress.py`. They are a record of this project, not a ranking, and nothing else publishes them.

Three things to know when reading those numbers:

- **The executable rebuilds byte-identical, but mostly not from our source.** The relink places each matched function at its retail address and takes everything unmatched from your retail file. The result has the same SHA1 as retail's `default.xbe`. That proves the matched functions fit where they belong; it isn't a full build from source.
- **Library code is counted apart.** About 1,500 functions in the executable are Xbox SDK library code. They are outside the game count above.
- **It has run on real hardware.** The maintainer launched the relinked build by hand on his Xbox and it reached in-game; that part is his observation, not a tool check. A matched function read back from the running game's memory with exactly retail's bytes.

## Build it from your own disc

The repository contains **no game files**: no executable, no disc image, no assets, no debug files (what it does hold from the game is listed under Contributing). You supply all of these yourself, and none of them is here:

- **Your own retail USA disc** ([redump entry](http://redump.org/disc/50478/)). Its `default.xbe` has SHA1 `2953b78229018a34e7f53e85bd34f124d51ef210`, and it is the only reference for what counts as correct.
- **The July 15, 2003 prototype preview disc,** which you source yourself, for its executable and debug files. The check of names and types is part of the gate and refuses to run without them, so you can't reach a passing result without this disc.
- **Your own copy of Visual Studio .NET 2003 Professional, RTM** (`cl` 13.10.3077, `LINK` 7.10.3077), never SP1. Each file is checked against pinned fingerprints.
- **Ghidra 12.1.4** with ghidra-xbe and ghidra-delinker-extension v0.9.2, **objdiff-cli 3.8.3**, and **Adoptium JDK 21.0.12**.
- **Windows 11, Git for Windows and Python 3.15.** Nothing has been tested on any other platform.

With those in place, from Git Bash, about 9 minutes of machine time:

```bash
git clone https://github.com/Gmooof2/Voodoo-Vince-Decomp.git && cd Voodoo-Vince-Decomp
git config core.hooksPath githooks
python -m pip install --require-hashes -r requirements.txt
cp config/local_paths.example.json config/local_paths.json   # then fill in where your files are
python tools/manifest.py verify           # about 20 seconds
python tools/check_env.py
python tools/proto_map.py --target retail-xbe
python tools/dup_report.py
python tools/delink.py ingest --fresh     # about 2 minutes
python tools/delink.py --fresh            # about 2 minutes
python tools/xdk_report.py
python tools/relink.py cut                # about 3 minutes
bash tools/run.sh gate -- python tools/gate.py   # about 90 seconds
                                          # -> "2797 passed, 0 failed of 2797"
```

[`SETUP.md`](SETUP.md) gives every step's details and expected result. Passing means exit code 0 and that final line. `python tools/gate.py --self-test` plants known errors and proves the gate catches each one: `controls: 231 failed as expected of 231`.

## Where the names come from

This project uses the PDB debug files from the prototype for most function, type and variable names. Function, type, global and field names carry a tag where they are declared, such as `proto-pdb:default.pdb`, so names from the prototype can be told apart from names found in retail. Local variable and parameter names come from the same files and carry no tag.

The prototype and its debug files are not in this repository. They never decide whether a function matches: that takes objdiff at 100% against the object cut from retail, and bytes equal to retail's. They do decide the gate's provenance check on names, types and locals, which is why a passing gate needs them. There is no mode without them.

This is a disclosure, not legal advice. The research done for this release found no source that settles whether a matching decompilation reproducing original code infringes.

## How it was made

This project was carried out by AI agents (Claude Code), directed by its maintainer, inside a written process: a roadmap, two human checkpoints per phase, and a growing set of rules drawn from what went wrong. The process is [ProjectArchitect](https://github.com/Druthulu/ProjectArchitect), and many of the rules come from [BFM-decomp](https://github.com/Druthulu/BFM-decomp).

The reverse-engineering side runs on Ghidra, with objdiff comparing each function to an object cut from retail. `tools/proto_map.py` compares the prototype's functions with retail's by masked bytes, which shows where the two are identical.

**About the history.** This repository is a fresh export, updated one new commit at a time, and the private development history is not included. Rule ids you'll see in tools and docs, such as `D42`, are in [`rules/`](rules/INDEX.md). Task ids such as `T4` point to a private journal, and nothing here needs them.

**The process, in public.** [`docs/process.md`](docs/process.md) explains how the work is run and checked: what the gate counts as a match, why every check is first shown failing, and how a public cut is made. [`rules/`](rules/INDEX.md) holds every rule, one file per id. [`docs/results.md`](docs/results.md) lists the observed results of each phase.

## Standards, and how the AI was used

**Accuracy.** A function is matched only when objdiff scores it 100% against the retail object and its bytes equal retail's, register allocation included. The gate re-checks every matched function on every run, and relinks the executable. Its checking tools are locked by fingerprint, and changing one needs the maintainer's review.

**Readability.** The code is matched, but it isn't finished. Placeholder names such as `field_1C` stay until there's evidence for a real name. 1158 `!FAKE` labels mark tricks kept to steer the compiler toward retail's output, and another 374 mark text copied from retail's own strings. An earlier cleanup pass tried to remove the roughly 190 trick labels there were then: it removed a few, could not test 11 of those left, and most of the others failed the trial. Labels added since were not part of it. The results are in [`docs/evidence/readability.md`](docs/evidence/readability.md). `python tools/annotations.py --check` is part of the gate and passes. It also lists 192 functions out of address order in their files, which stop compiling if moved or can't be moved; those are reported and don't fail it.

**How the AI was used.** Agents wrote the code, the tools and the docs. The maintainer set the scope, approved every change to the checking tools, and ran the Xbox test. The gate, not the model, decides what counts as matched. Names and structure come only from recorded evidence, never from a guess. This README was also drafted by an AI agent, from a checked list of facts, and approved by the maintainer. Anything sent to other projects is written by the maintainer, and no tool here contacts community services.

## Tools from this project

These may be useful to other Xbox decompilation projects:

- `tools/relink.py` links matched objects with retail's bytes into a byte-identical `.xbe`.
- `tools/proto_map.py` maps retail functions to a prototype's by masked-byte identity.
- `tools/name_sites.py` names unresolved addresses in retail functions from the same sites in identical prototype functions, re-checking the identity first.
- `tools/xbdm_probe.py` compares a function in a running Xbox's memory with the retail file, read-only.
- `tools/match_one.py` builds one function's unit and compares it, a quick check while matching. Only the gate decides.

## Contributing, and the no-game-data policy

No game file or prototype file may enter the repository: no executable, no disc image, no assets, no debug files, no objects, no databases. Names and types from the debug files are the disclosed use described above. Beyond those, two kinds of text come from the game:

- **Text strings.** Where a function uses a string, the source spells it out exactly as retail has it (about 1100 lines, 374 of them labelled). Some of these are the original studio's build paths.
- **Paths in the unit list.** `config/retail/units.toml` lists the original source file paths recorded in the prototype's debug files: under `d:\beep`, `D:\xboxfre-jun03\private` and `C:\Program Files\Microsoft Xbox SDK`.

The audit (`tools/audit_public.py`) runs in the git hooks locally and on GitHub on every push and pull request. GitHub's run has no local config, so it doesn't check private values. Byte identity itself is checked locally, because GitHub has no copy of the game.

Issues and pull requests are welcome. A match has to pass the gate, and a name has to come with its evidence. Open an issue first if you aren't sure something is allowed. Accepted changes are applied in the private working copy and reach this repository in the next export, so a pull request is closed rather than merged, with you credited as co-author.
