## Text

`corr-verified` is an accepted pin status for a name whose target has no byte route of its own. It sits beside `disasm-verified`, which keeps meaning the target's own bytes were checked (D114). Only these routes write it:
- Globals in bss, EH throw info (`__TI`) and initialized globals, check tag `+site-bundle`: at least 2 distinct caller rows whose sites agree on the name, 0 conflicting sites, the name is a unique PDB public, and every site lies inside the pin's extent.
- Vtables, check tag `+slot-bytes`: every slot's retail bytes equal default.exe's, the same slot count, and at least 1 agreeing site.
- Literals are unchanged: string bytes and `__real@` value bytes give `disasm-verified` (D114), never `corr-verified`.
D102 stands: `site-corr` alone stays refused. A pin that fails its route keeps `site-corr` with one reason. The acceptance lands in the tools and in the pin-row check (D119) in 4.2 T5; passes T7 and T8 write the pins.
