# Verifier lock: fingerprint the verifier, and the imports it actually loaded

Problem: an agent that cannot pass a check edits the checker (R0-026, Momo5502). Fix: the gate's first check hashes its own files.

- Keep the list as a constant in the lock tool (LISTED), not derived at check time; the fingerprint file
  (`<sha256>  <path>`, sorted) is written by `write` and is itself a review-only artifact.
- `write` computes the closure: import the gate (and every tool it runs as a subprocess) in a child process, collect
  `sys.modules` `__file__`s under `tools/`; refuse when the closure has a module LISTED lacks. The list cannot drift.
- `check` at gate start: fingerprint missing/empty, listed file missing, sha mismatch, extra path, and any module in
  this process's `sys.modules` under `tools/` not listed. Repeat the import part after the last layer (lazy imports).
- On lock failure stop at once (rc 1): an unproven verifier's other verdicts mean nothing (overrides "report every layer").
- Controls: build a scratch repo root holding copies of LISTED + a fingerprint written for them; assert it passes, then
  mutate one thing (one byte, delete a file, delete/empty the fingerprint, add a fake `tools/_unlisted.py` to the
  module list). Never mutate the real files. Count a control only if rc 1, at `lock`, and no later layer ran.
- Trap: write the fingerprint as the very last step; any edit to a listed file afterwards invalidates it.
- Trap: a lazy import inside a listed module (here `coff_info.check_xbe` -> `proto_map`) is outside the closure until called.
Ref: tools/verifier_lock.py, tools/gate.py (1.5 T6).
