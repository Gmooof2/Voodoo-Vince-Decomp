# C0178 — Concurrent JSONL append on Windows: open('a') tears rows; byte lock past EOF; race control staggers
tags: windows,python,append,jsonl,ledger,lock,msvcrt,concurrency,match_one,parallel,workdir,control · date: 2026-11-01 · phase/task: 4.1/T6 · origin: T6 ledger stress

- `open(path, "a")` is not safe across processes here (Windows 11, Python 3.15): one buffered write per row still tore
  and lost rows. 16 processes x 200 rows through the real path: about 1,850 of 3,200 rows survived, about 145 lines invalid,
  in 6 of 6 runs. Do not assume O_APPEND atomicity on this machine; run the stress first.
- Fix for a shared JSONL: `msvcrt.locking` on the file itself, at a byte past any possible end (`1 << 40`), mode `r+b`:
  seek there, lock with `LK_NBLCK` in a short retry loop, seek to the end, write, flush, seek back, `LK_UNLCK`. No reader
  waits (the region holds no rows), no sidecar in the tree, the OS frees it if the holder dies, the file does not grow.
  After: 3,200 of 3,200 valid, 3 of 3 runs. `tools/match_one.py` `_append_row`.
- Prove the harness can see it: same check with a seek-to-end writer as negative control (about 1,130 valid, 230 invalid),
  and compare the set of row ids, not only `json.loads` of each line: most damage is missing rows, not bad lines.
- A workdir option's folder is a sibling of the default, never inside it: a default run wipes its own folder whole.
- Race controls need tight staggers: a match_one run here takes about 0.5 s, so overlap shows only for starts under
  about 0.1 s; later starts passing prove nothing. Absence in a few trials is not safety.
