# C0052 — Hash pins taken in an autocrlf=true working copy fail on LF clones
tags: git,windows,crlf,verifier,lock,pin · date: 2026-10-26 · phase/task: 1.8/T5 · origin: T5 clone gate FAIL lock

# Hash pins taken in an autocrlf=true working copy

- A tool that hashes tracked files (verifier lock, manifest sidecar) pins the WORKING-TREE bytes. With
  `core.autocrlf=true` a file rewritten by git checkout/restore is CRLF (`git ls-files --eol` -> `i/lf w/crlf`)
  while files written by editors/tools stay LF, so the pin matches only this working copy.
- An LF clone (`-c core.autocrlf=false`, C0006) then fails the lock on exactly those files.
- Check before any re-pin: `git ls-files --eol <listed files> | grep w/crlf` must be empty; restore the file from
  the HEAD blob (`git show HEAD:<f>` written by Python) and pin that.
- Diagnose: sha256 of `git show HEAD:<f>` vs the pin; CRLF-converted blob == pin proves it.

Source: phase 1.8 T5 (tools/byte_compare.py pinned 75e602e4 = CRLF of blob e444797d).

## Prevention (1.8 T10)
- `.gitattributes` `<f> -text` for every hashed tracked file: no eol conversion on add or checkout, so committed ==
  working == pinned bytes on every clone. Not `eol=lf`: it normalises on add, so a CRLF working file still gets
  pinned as CRLF while clones get LF (same failure, hidden).
- After adding the attribute `git status` may show `M` with no content diff (stat cache); `git hash-object <f>` ==
  `git rev-parse HEAD:<f>` proves it clean.
