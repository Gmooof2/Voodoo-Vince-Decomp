# Listing a multi-module COMDAT row can break another unit's pin_rows bracket

- Symptom: match_finish_batch gate `N passed, 0 failed; FAIL globals: pin_rows`, `route-bracket:outside-bracket` on bracket pins of a unit the batch never touched. precheck passes: it runs no pins layer.
- Mechanism: `tools/pin_rows.py:483-536` `anchors(m)` takes every proc of PDB module m with a public name in matched_set. A COMDAT proc (e.g. an STL `list<T>::clear`) appears in several PDB modules; once its row is listed it can become a foreign module's nearest anchor while its retail VA lies in another unit, so the window start w0 jumps past the pins.
- Isolate: add each batch row singly to HEAD's list and re-run `bracket()` for the failing pins (5.4 T19.c2 scratch, not kept: a ~30-line script patching pin_rows MATCHED to a scratch list, then calling `bracket()`): cheap, no gate.
- Fix now: re-guard the row with the blocker (D29). Tool fix (LISTED, needs a plan decision): use an anchor only when its retail VA lies inside the module's unit text.
- Case: 5.4 T19, 0x000C1AA9 list<ScriptTimerEvent>::clear (proto 0x0040072B, 5 modules) vs Init.obj pins 0x000113EB, 0x00011473.
