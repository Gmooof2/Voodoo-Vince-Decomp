# Chain in-memory candidate classes: a settled class becomes the next class's caller set; cache per-body evidence

When one evidence class can only act after another names its callers (5.4 T9: creationFunc bodies are reached only
by a `push imm32` inside their unnamed `X::RegisterMe::RegisterMe` ctor), size both in the tool without a writer:
1. Compute the first class's settled pairs eagerly, before the `PRED` grid (pool_buckets.lane_sizing): a set of
   (P, t). Its predicate is then a set lookup.
2. Feed those pairs into the second class's index exactly as accepted table callers are fed (the same abs/rel mask
   loop over `img.match`), tagging each site's source (`accepted` | `chain`) in a parallel dict so the output can
   split rows settled via accepted callers from rows settled only through the chain. Skip a chained body that is
   already an accepted caller, so no site counts twice.
3. Order `PRED` so the chained class comes last; the generic plants, teeth mutation, agreement, per-class, residue
   `would:` and edge-proposal lines then cover both classes with no new code path.
4. A wide grid (764 rows x 776 bodies) stays cheap when the per-body evidence is cached once (the retail literal at
   the body's abs dest in `.rdata`/`.data`, C0367) and the proto literal once per row (`name_sites.str_len`), so the
   predicate is dict lookups and `img.match` runs only on equal-literal pairs (56 s for the whole tool).
5. When the chained class's targets may not be Ghidra entries, print where each chained dest lands as a checked sum
   (entry / gap / non-entry hit of the row / not a hit / conflict): 57 of 72 creationFunc dests were non-entry hits,
   which is a ruling (R183 start evidence), not a tool gap.
