# C0035 — delinked target: rel32 into its own section never gets a relocation
Superseded by C0058 (2.1 T3/T5): cause = exporter "Trim superfluous PC-relative relocations" option; fixed by the delink REL32 post-pass on every unit (0 unrelocated of 807).
tags: delink,relocation,objdiff,coff,rel32 · date: 2026-10-25 · phase/task: 1.5/T12 · origin: T12 relocscan residue

Problem: a delinked target object has a call/jmp rel32 with no relocation although the instruction lies inside a
Ghidra function and the target is a real function; the same call in our MSVC-compiled object carries a REL32.
Mechanism: the delinker (ghidra-delinker-extension, pin in `docs/ops/tools.md` "Ghidra toolchain") never emits a
relocation for a PC-relative field whose target lies in the same exported section: at retail-2953b782, 0 of 1013
such sites relocated, 7798 of 8886 rel32 sites leaving the section relocated (T12 scratch classify over 928 fns
>= 64 B). Same-section rel32 is position-independent inside the section, so the delinker leaves the raw
displacement.
Scale (T12): 31 fns >= 64 B reloc-free for this reason only; 935 unrelocated sites in 363 partially relocated fns.
Open: whether objdiff scores such a call as DIFF_ARG_MISMATCH against our relocated call in multi-function units
(the gate self-test's 4 fns passed; none was examined for this). Check a unit with an intra-section call before
assuming a 100% is reachable there.
Check: `PY tools/delink.py relocscan` reason `intra-section branches only`; per site, `coff_info` relocs vs.
`proto_map.mask_proc` rel sites whose target falls in the function's own object section.
Related: C0034 (no Ghidra function -> no code relocs at all).
