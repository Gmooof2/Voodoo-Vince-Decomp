# Promote a site-corr data pin by its retail bytes (name_sites --promote-data)

Use: a data pin named by site correspondence (`site-corr`) blocks rows as `provisional`; promote it only on retail bytes.

- Compare retail XBE bytes at the pin VA with default.exe bytes at the PDB public of the same name over the TPI size
  of the S_GDATA32/S_LDATA32 record at the public's seg:off. Gotcha: those records carry UNDECORATED names
  (`inflate_mask`, `DrawLevel::_mirrorsEnabled`); match by VA, then name N == r, `_`+r, or `?`+reversed scope+`@@`.
  A literal "record named N" lookup finds none (88 of 88 no-type in 3.3 T8).
- Pointer fields = offsets the prototype `.reloc` covers; compare by name (proto-target publics vs accepted names at
  the retail target), iterate to a fixed point. Require one non-zero byte or one agreeing pointer (zeros identify nothing).
- Vtables pass only when every slot's retail callee is already named with an accepted status; at 3.3 none were
  (slot callees unnamed), so vtables wait on callee naming, not on this route.
- Retail `.bss` (no raw bytes) cannot be checked: 68 of 249 at 3.3.
- Planted control: real pin VA + a wrong global's name through the real in-place write path; refused, git diff empty.
- Evidence: docs/evidence/correspondence.md "## Data byte route (3.3 T8)"; tools/name_sites.py `--promote-data`.
