# Completeness marker for a multi-stage generated output dir

Problem: a long generator (delink --fresh: ingest, export per chunk, post-pass, hashes, report) leaves a partial dir
when it dies midway; readers that refuse only on missing files read a mix of old and new outputs.

Move:
- Delete the marker as the generator's FIRST filesystem action (before any stage that rmtree's or rewrites inputs
  the readers also use, e.g. a sibling `applied/` export).
- Write it LAST, after every content check passed (D36), as one exact line over a content digest:
  `cut-complete v1 hashes-sha256 <hex64> objects <N>` (sha256 of the hashes file bytes; N == its line count).
- Every reader validates it first (exact regex fullmatch on the bytes, recompute the digest, compare N) and refuses
  exit 2 naming the marker path. One marker covers every dir the generator rewrites.
- Side tools that write single diagnostic outputs go to a sibling dir outside the marked dir, so they neither
  invalidate it nor get swept into a reader's glob; readers iterate the hashes file, not `glob("*.obj")`.
- Negative control: copy the real dir to scratch, monkeypatch the dir resolver (`cut_dir`) to the copy, run each
  reader's main() with the marker removed and with a wrong digest; each must exit 2 naming the marker.

Locked readers (verifier lock) never import the unlocked helper: they implement the same format and assert it.
Source: tools/delink.py cut_dir/cut_check/write_marker; docs/ops/tools.md `## delink --fresh / --repro`.
