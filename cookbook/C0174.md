# Reordering function bodies in a matched unit: what keeps the bytes

Trial: 62 moves that would put FUNCTION blocks in VA order, each through the gate's core on a scratch copy (4.1 T2,
`docs/ops/validation.md` "4.1 Lint and annotation evidence"). 16 kept an equal obj, 11 changed obj layout only, 20 failed
to compile, 14 could not move by shape, 1 failed bytes.

- Moving an inline member across an access label changes its mangled name (`IAE` protected, `QAE` public). It compiles
  silently and fails `defined`, objdiff, bytes and relink (`EvilVince.cpp:279`). A same-scope check does not catch it:
  compare the access label too. Related: C0096.
- A moved body lands above its class or a needed declaration most of the time (C2653, C2065; C2661 for a placement
  `operator new`). Never edit the block to fix that.
- A real source move can leave the obj identical (masked COFF TimeDateStamp); source order does not always set emission
  order. Cause not pinned. A changed layout still passed relink and every function here.
- A failed build makes the provenance layer refuse (`REFUSED locals: /Z7 compile`), so a compile-failing run gives no lint
  evidence.
- Fresh process and fresh `src` copy per run; repoint scratch at import (C0163). A build failure stops relink, so an
  all-in run needs a second run over only the files that compile.

Applied 4.1 T4 (21 files, 62 to 35 order lines). A longest-increasing keep must allow equal VAs (`<=`), or a FOLDED pair gets split. Add a per-line check of text and enclosing access label before and after (`access_lines`, T4.c2). `derived/gate/last.json` `body_sha1` comes from the matched-set row, not the built object, so it cannot show a source change kept bytes: the evidence is `bytes`, objdiff and relink passing on every row from a fresh build.
