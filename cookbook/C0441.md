tags: control,dnf,verifier_lock,self-test,gate_controls,provenance_lint · date: 2026-11-10 · phase/task: 5.5/T13 · origin: T13.c1 t13c1-dnf vs dnf2

# DNF run of a new gate control against a locked tool's unfixed copy

- Problem: a new control has to be shown `DID NOT FAIL` on the unfixed tool. But the tool is LISTED, so if you swap in HEAD's copy and run `gate.py --self-test`, the lock layer stops the gate first (fp mismatch). The control then "fails" for the wrong reason, and that log proves nothing (5.5 T13.c1 `t13c1-dnf.log`).
- Move: copy the working tool aside, put HEAD's copy back (`git show HEAD:tools/<tool>.py`), run `PY tools/verifier_lock.py write`, and run the self-test. Expect `0 of K` for the new controls (`t13c1-dnf2.log`). Then restore the fixed copy and run `verifier_lock write` again.
- Check: in the DNF log, each new control's line names the check's own cause or `DID NOT FAIL`, never `lock`.
- A control that tests code already in place (e.g. pin-two-names-stale, which tests pin_rows' existing stale path) has no DNF. Say so in the log. For mutation-style DNF of pin_rows, see C0440.
