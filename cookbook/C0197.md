# A consistency check that re-implements a shared rule drifts: call the rule

Context: 4.3 T1. `naming_levers.py` `mk()` asserts its own blocker list equals `family_census.make_row`'s ("row 0x0009D80A:
blockers differ from make_row", 4.2 T13). 4.2 T9 moved `make_row` onto `candidates.accepted(status, target, funcs)` (D115:
CALLEE_STATUSES count as accepted on func-table targets); `naming_levers.blockers_of` kept its own `OK_STATUS` tuple, so every
row with a D115-accepted callee site disagreed. Fresh inputs never clear such a refusal.

Move: grep for every filter on the same statuses (`OK_STATUS`, `PIN_STATUSES`, `in units_seed.STATUSES`) and make each call the
one shared predicate (`candidates.accepted`). A tool that cross-checks another tool's output is the first to break when the rule
moves; the assertion did its job, the fix is in the duplicate, never in the assertion.

Follow-on: renderers written for one generation's start (hard `next()` lookups of an owner such as gSettings 0x00238E98) fail
with StopIteration once that owner stops blocking; guard with `next(..., None)` and print "no row carries it today". `expect()`
and `Figs.one` only record "moved" and never fail.
