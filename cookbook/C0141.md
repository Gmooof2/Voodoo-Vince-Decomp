# cl 13.10 /O1 commutative x87 add order and cvttss2si destination: what moves them (3.3 T21)
- Two sibling adds `a.x = s.u + a.x; a.y = s.v + a.y;` in one loop share an operand-order tie-break: naming one operand (`float ly = s.v; a.y = ly + a.y;`) flips that add to retail order (`fld [ebx+4]; fadd [eax]`) but reverses the other (Sprite::Render, tie 98.6). Naming one side alone does not fix both; untested: name both.
- Deleting upstream code (rotation block, init loop) never flipped the y add; it only moved the x add's order: the tie-break is local to the pair, not driven by distant numbering.
- `_mm_cvtt_ss2si(...)<<24 | m` computes straight into its destination register; a named local (int or unsigned) before the loop still gives `cvttss2si ecx` or worse (`_color` preloaded into edx, 94.35). Retail `cvttss2si eax; ...; mov ecx,eax` was not reproduced by any D78-legal form: wall.
- Replacing a `__forceinline Apply(v)` value wrapper by the PDB two-arg call `Apply(v, r); v = r;` scored lower (97.87 vs 98.6) here.
