# Side effects inside call arguments move cl's scheduling; named x87 term stand-ins fix term order

- Retail scheduled `add edx,_vShaderBones` before `push 12` only when both loop increments sat inside the call arguments: `for (i = 0; i < n;) F(i++ * 3 + 60, &tbl[*p++ * 3], 12);` (`// !FAKE:`; ModelResource::SetBoneTable 0x000BAAA2 matched at attempt 14). Increments in the for-header, `*p++` alone, the PDB inline wrapper, or defining the table in the unit gave 94.29 or worse.
- x87 product order in a long expression: hoist one product into a named float stand-in (`float v4 = a.x * b.x;`), one at a time, each moving objdiff (SphereHitTag 0x000DF873 99.31 -> 99.90). Operand order inside a product (`equation.y * v10` vs `v10 * equation.y`) did not follow source order there.
- Frame slots did not move for declaration moves or renames; taking a local's address moves its slot but changes code (C0327).
- A `pop esi` placement followed only the form of a preceding float compare (`if (0.0f > v6)` moved it but changed the compare).
