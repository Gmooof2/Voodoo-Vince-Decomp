# A source-hash lock does not cover the bytecode Python runs

- A verifier lock that sha256s `tools/*.py` (`verifier_lock.check`) proves the `.py` files, not the code objects
  the interpreter executes. CPython loads `__pycache__/<mod>.cpython-3xx.pyc` instead of the source whenever the
  pyc header's mtime + size equal the source's (default timestamp validation). `module.__file__` still names the
  `.py`, so a `sys.modules` check sees nothing; `__pycache__/` is gitignored, so review sees nothing either.
- Plant (scratch only): `importlib._bootstrap_external._code_to_timestamp_pyc(compile(altered, src, "exec"),
  int(os.stat(src).st_mtime), os.stat(src).st_size)` written to `importlib.util.cache_from_source(src)`.
- Verified on CPython 3.15.0 (3.5 T3): plain import ran the planted code; with `PYTHONPYCACHEPREFIX=<fresh dir>`
  the source was compiled and the plant ignored (`__spec__.cached` moved under the prefix).
- Close it: set `sys.pycache_prefix` to a fresh empty dir before the verifier's own imports, pass
  `PYTHONPYCACHEPREFIX` to every child Python, and have the lock refuse when the prefix is unset or a listed
  module's `__spec__.cached` lies under the repo's `__pycache__`. (`-B` only stops writing pycs, not reading them.)
- Out of reach of any repo lock: `sitecustomize`, `.pth` files, a swapped interpreter.

Source: phase 3.5 T3, finding F1 of R3.5-008 (tools/gate.py:66-74 imports before the lock at :150).
- 3.15: `module.__cached__` is gone and `ModuleSpec.cached` is lazy, computed with the pycache prefix in force at first access; a check must read `spec.cached` while the prefix it tests is set (3.5 T4.c1, verifier_lock.pycache).
